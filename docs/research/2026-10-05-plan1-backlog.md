- Decided (by design, from the 04e8064 review): the internal-error result from `respond()` is plain text, `Internal error in <tool>; see the server log`, not the section 8 JSON payload. ## Lowlands trial (2026-10-12)

- Done: a graph spec can hold one Combiner only. A device's spec name is its identity, and World Machine ignores a rename of a Combiner (v3 fact 80), so a second Combiner would share the name `Combiner` and conflict. A layered terrain (base, hills, masked mountains) needs three. Workaround used: `add_device` the extra Combiners and wire them with `connect_devices` by `#<id>`, outside the spec. A fix would let a spec entry name a device by `#<id>`, or give an added Combiner a spec-only alias that the server maps to its id. Resolution (v3 spec revision 6): a device entry takes an optional `id` and manages that device under a spec-local label, and a Combiner entry without `id` that matches no device must be named exactly `Combiner` with type `Combiner` (any other name is a plan conflict pointing to `add_device` and `id`); commits 2b510e5, 9ce8f38, 8cdd12c, 8c9994b, 3a5835c.
- Done: `disconnect_devices` refuses a wire whose source shares its name with another device (`world-machine-wire-editor.ts:107-111`), so once several Combiners exist, no wire leaving a Combiner can be removed through the MCP, and renaming does not help for a Combiner. Seen live: moving Erosion's input from one Combiner to another failed with this refusal. A fix (reasoning, not tested): an input holds one wire, so after `wire disconnect #<src> #<dst>.<port>` the destination input reading `<- (none)` confirms the removal whatever the source names are, and an input still wired means the wire was another device's and nothing was removed. Resolution (v3 spec revision 6, fact 82): the wire editor and the planner read the candidates' connections and take the one whose output lists the input (`resolveWireSource`); only an unresolvable source is refused, naming the candidate ids; commits ff79611, db474f6, e3a3600, 4d7fde0.

Resolution (enum-options design, 2026-10-12): the console has no listing command (fact 83), so the options of all 111 enum parameters of build 4067 were captured once (`raw/enum-options.txt`, fact 85) into a catalog shipped with the server (`src/adapter/out/worldmachine/enum-options.4067.json`, generated by `scripts/build-enum-catalog.mjs`); `get_device` lists them per enum row and says in `enumOptionsNote` why a row has none; options are listed only when the device's parameter names match a new device's of that type, since default-project devices can be older versions. ## v3 out-of-scope features (spec section 10, added 2026-10-15)

Features the v3 spec (section 10) leaves out, now candidates. Each needs a design (brainstorm, spec revision or new spec, plan) before any code.

- Done: Scene settings in a graph spec: let `plan_graph` and `apply_graph` set what `configure_scene` sets (extents, resolution), planned, diffed, and rolled back with the devices. Open questions: whether `snapshot restore` reverts every scene setting (v2b fact 69 shows it reverts the resolution; the extents were not checked), how a scene change is compared for a second plan, and whether a resolution change belongs in the same apply as device edits. Resolution (2026-10-15): v3 spec revision 8. A spec's optional `scene` (name, origin_km, size_km, resolution of the current scene) is one `set-scene` step before every device step, compared exactly for name and resolution and at two decimals for origin and size; a locked scene with a difference is a conflict; the apply result's `scene` shows `{ before, after }`; a restore reverts all four (fact 101, raw/v8-scene-restore.txt). Live graphs 10/10. Commits: 56285fc..0d9fd31.
- Done: Spec files and templates on disk: `plan_graph` and `apply_graph` take a path to a spec file instead of inline JSON, and a template is a reusable spec. Open questions: the path policy (the same roots as project files?), a file format and its version, whether a template takes parameters, and how a file changed between plan and apply affects the planId. Resolution (2026-10-15): docs/superpowers/specs/2026-10-15-worldmachine-mcp-graph-templates-design.md (v3 revision 9). plan_graph and apply_graph take exactly one of `spec` and `template: { path, parameters? }`; a template is a `.json` file inside the allowed roots (at most 1 MB, strict UTF-8, one leading BOM stripped, regular file, opened non-blocking) with typed parameters (number, integer, string, boolean) and `{ "$param": "<name>" }` values; a file without `template` is a plain spec; the planId hashes the filled spec, so a changed file is stale. Listing or saving templates stays out of scope. Commits: 5acac3a..db03498.
- Won't fix: Groups and layout in a graph spec: group membership and device positions. Today groups can be listed, enabled, disabled, and built (`list_groups`, `set_group_enabled`, `build_project` group mode), but creating a group and assigning devices happen only in the World Machine window, and `organize_devices` is the only layout command. Needs a capture first: which console commands, if any, create groups, assign members, or move a device. Resolution (2026-10-15): blocked by World Machine. The capture raw/groups-layout-probe.txt shows build 4067's console has no command to create, rename, or delete a group, to assign a device to one, or to read or set a device position: `group create|new|add|assign|remove|delete|rename` and `device group|move|position|pos|setpos|place|location` all answer `Unknown command`, and `debug list` exposes no position or membership. Editing the `.tmd` file is ruled out by design (World Machine is the only program that reads or writes it). A feature request for the World Machine forums is in docs/research/2026-10-15-worldmachine-console-groups-layout-request.md (user ruling 2026-10-15).
