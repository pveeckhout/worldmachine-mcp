## Decisions deferred to the Plan 2 spec

- Done: `CRASHED` doubles as the "not running / shutting down" refusal. Spec section 8 defines it as an unexpected exit. (b1af885 added `SHUTTING_DOWN`, spec section 8; `world-machine-session.ts:77`. `CRASHED` remains only for a write after exit, `world-machine-process.ts:121`, an exit during a batch, `command-queue.ts:41`, and a defensive no-queue check, `world-machine-session.ts:110`.)
- Done: A `START_FAILED` hint for display errors (`qt.qpa.xcb: could not connect to display`), pointing users to the README's Linux display variables. (b1af885: `world-machine-process.ts:14-16, 80`, test `adds a display hint when World Machine cannot open its window`; spec section 8, `START_FAILED` row.)
- Done: The dirty-state wording of `CRASHED` (spec section 8). No Plan 1 code sets `dirty`. (b1af885: `LOST_CHANGES` at `world-machine-session.ts:35`, used at :122 and :315-317; spec section 6 sets `dirty`.)
- Decided (by design, from the 04e8064 review): the internal-error result from `respond()` is plain text, `Internal error in <tool>; see the server log`, not the section 8 JSON payload. Section 8's payload requires a `code: ErrorCode`, and no code fits a server bug (`START_FAILED` is reserved for startup, `UNEXPECTED_OUTPUT` for parser mismatches); an `INTERNAL_ERROR` code would be a spec change to section 8 and to the `ErrorCode` union. The result is still `isError: true`, and only bugs reach this path, so a client gains nothing from parsing it. Revisit only if a client needs a machine-readable code for it.
